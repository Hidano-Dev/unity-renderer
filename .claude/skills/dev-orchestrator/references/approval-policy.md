# Approval Policy — 承認代行の判定基準

Orchestrator が cc-sdd の各承認ゲートを代行するときの判定基準。
ゲートごとに「AUTO-APPROVE 条件」「差し戻し（修正再実行）条件」「エスカレーション必須条件」を定める。

## 共通原則

1. **代行できるのは、ポリシーで機械的に判断できる承認だけ**。基準に照らして曖昧さが残る場合は
   必ずエスカレーションする（承認側に倒さない）
2. エスカレーション必須条件は AUTO-APPROVE 条件より**常に優先**する
   （Reviewer が GO でも、エスカレーション条件に1つでも該当すればユーザー確認）
3. すべての判定は根拠つきで進行ログに記録する。根拠は「どの基準に照らして何を確認したか」を
   1〜3行で書く
4. 差し戻し（同フェーズ再実行）は各ゲート最大 2 回。超えたらエスカレーション

## Gate S: 着手前スコープ確認（init → requirements）

**このゲートは承認代行の対象外。新規モードでは必ずユーザー確認を行う**（全自動フローに入る前の
唯一の定例確認。以降のゲートを代行モードで進めることへの同意を兼ねる）。

- 確認内容: feature 名 / 解釈したスコープの要約（含む・含まない）/ brownfield 判定 / 停止予定フェーズ
- 選択肢: 「このスコープで続行 (推奨)」「スコープを修正する」「中止」
- 修正指示を受けたら説明を修正して spec-init からやり直し、再度 Gate S を行う
- 再開モードでは進行ログに Gate S 通過記録があればスキップする（記録がなければ実施する）
- **Gate S は定例確認であり、エスカレーションとして数えない**（「実装開始の特例」の判定に含めない）

## Gate A: 要件承認（requirements → design）

対応する cc-sdd 操作: 通過時に `/kiro:spec-design <f> -y` を実行（requirements が承認扱いになる）。

**AUTO-APPROVE 条件（すべて満たすこと）**:

- spec-requirements の SubAgent サマリにエラー・未解決の質問がない
- requirements.md に「TBD」「要確認」等の未確定マーカーが残っていない（Grep で機械的に確認）
- brownfield の場合、validate-gap が実装戦略上の重大な矛盾を報告していない
- 要件が `.kiro/steering/` の方針（product.md / tech.md / structure.md）と矛盾していない

**差し戻し条件**（フィードバック付きで `/kiro:spec-requirements <f>` を再実行）:

- EARS 形式違反・要件 ID 欠落などの構造的問題
- validate-gap が指摘した、要件の記述修正で解消できるギャップ

**エスカレーション必須条件**:

- 要件に複数の合理的な解釈があり、選択次第でスコープが大きく変わる
- 元の依頼に含まれない機能・スコープを追加しないと要件が成立しない
- 外部サービス連携・継続的コストの発生が新たに必要になる
- 個人情報・認証・課金・セキュリティに関わる要件の追加や変更
- 既存データの削除・移行・スキーマ変更を伴う
- steering の方針と矛盾し、どちらを優先すべきか判断が必要

## Gate B: 設計承認（design → tasks）

対応する cc-sdd 操作: 通過時に `/kiro:spec-tasks <f> -y` を実行（design が承認扱いになる）。

**AUTO-APPROVE 条件（すべて満たすこと）**:

- `/kiro:validate-design <f>` が GO（軽微な注記つき GO は許容し、注記を進行ログに転記）
- 要件トレーサビリティ・境界セクション・File Structure Plan が埋まっている
  （validate-design のメカニカルチェック結果で確認）
- 設計が既存アーキテクチャの延長で、下記エスカレーション条件に該当しない

**差し戻し条件**（指摘をフィードバックとして `/kiro:spec-design <f>` を再実行。merge モード）:

- validate-design が NO-GO だが、指摘がすべて設計ドキュメントの修正で解消できる内容

**エスカレーション必須条件**:

- 新規の依存ライブラリ・ミドルウェア・インフラの導入を伴う
- 公開 API / DB スキーマ / 永続データ形式の破壊的変更を伴う
- 既存コードの広範囲なリファクタリングが前提になる
- 認証・認可・課金・個人情報の設計判断を含む
- validate-design が 2 回連続 NO-GO
- 設計の過程で要件の欠陥が見つかり、要件フェーズへ戻る必要がある

## Gate C: タスク承認（tasks → implementation）

対応する cc-sdd 操作: 通過時に `spec.json` を直接更新
（`approvals.tasks.approved: true`、`ready_for_implementation: true`、`updated_at` 更新）。

**AUTO-APPROVE 条件（すべて満たすこと）**:

- 全要件 ID がいずれかのタスクにマッピングされている（tasks.md の要件参照を機械的に確認）
- タスクがすべて実行可能な粒度（コンテナタスクだけの空セクションがない）
- 下記エスカレーション条件に該当する破壊的タスクがない

**差し戻し条件**（`/kiro:spec-tasks <f>` を再実行）:

- 要件マッピング漏れ・粒度異常など、タスクドキュメントの修正で解消できる問題

**エスカレーション必須条件**:

- データ削除・DB マイグレーション・デプロイ・外部への送信/公開を含むタスクがある
- design.md の境界（Boundary Commitments）の外に触れるタスクがある
- タスクの実行順序に依存関係の矛盾があり、解釈で補う必要がある

## Gate D: 完了判定（implementation → done）

このゲートに「承認」はない。完了報告か、失敗のエスカレーションかの二択。

**完了報告（確認不要の通知）**:

- spec-run の全タスクが OK かつ validate-impl に重大指摘なし
- validate-impl の軽微な指摘は完了報告に「残課題」として転記する

**エスカレーション必須条件**:

- FAIL / TIMEOUT のタスクがある（部分成功を含む）
- 連続失敗ガードで打ち切られた
- validate-impl が要件未達・回帰・セキュリティ問題など重大な指摘を報告した

エスカレーション時は「修正して再実行 / 現状で受け入れて PR 化 / 中断」を選択肢として提示する。
**Orchestrator 自身が検証起点の修正ループに入ってはならない**（spec-run の無人実行方針と同じ）。

## Gate E: PR 作成（implementation → PR）

対応する操作: 通過時に `git push -u origin <branch>` → `gh pr create` を実行。

**AUTO-PROCEED 条件（すべて満たすこと）**:

- Gate D を通過している（またはエスカレーションでユーザーが「現状で受け入れて PR 化」を選択済み）
- 作業ブランチがデフォルトブランチ以外の作業用ブランチである（`feature/` のほか
  `fix/` `chore/` `docs/` 等の接頭辞も可。デフォルトブランチから直接 PR を作らない）
- working tree に spec-run のコミット外の予期しない変更が残っていない（`git status` で機械的に確認。
  `.kiro/` 配下の spec / 進行ログの未コミット分は、あればコミットに含めてよい）
- push / PR 作成の対象がこのリポジトリの origin である（別リモートへの push はしない）

**エスカレーション必須条件**:

- working tree に出所不明の変更が残っている（黙って含めたり破棄したりしない）
- push が reject された（force push で解決しようとせず、状況を報告して指示を仰ぐ）
- ベースブランチが判定できない、または PR の宛先に迷いがある

`gh` CLI が使えない場合は push まで行い、PR タイトル・本文案と作成 URL を完了報告に含めて
縮退する（エスカレーション不要。正常な縮退として進行ログに記録する）。
PR 作成後のレビューとマージ判断は人間が行う。**Orchestrator はマージしない**。

## 実装開始の特例

Gate C 通過後、`--stop-after tasks` が指定されていなければ spec-run を自動開始してよい
（Gate S でユーザーが全自動フローに同意済みのため）。ただし、Gate A〜C のいずれかで
1 回でもエスカレーションが発生していた場合は、実装開始前に確認を 1 回だけ行う
（前提が揺れたフローで長時間の無人実行に入らないため）。Gate S の定例確認はこの判定に含めない。
